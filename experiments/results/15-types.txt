二、做不到 / 有限制的条目与原因
-------------------------------

1. 只读 prop 不能赋值（做不到）。解构出来的是普通局部变量，TypeScript 没有“只读的解构绑定”，也没有办法让 `size = 'sm'` 报错
   （02-components.tsx 的 ReadonlyHole 留了说明）。能在编译器里做：同一个函数内，对不是 _bindable / _state 默认值的解构绑定赋值，语法层就认得出。
2. key 只在列表行（做不到）。JSX 表达式的类型是同一个 JSX.Element，类型层看不到“这是不是 map 的返回值”。所有元素都收 key，位置由编译器诊断。
3. “声明了 _bindable 的 prop 才可绑”：类型层读不到函数体里的默认值，只能约定“有 onXxxChange 回调的 prop 可绑”。
   BindableProps<{ value: string }> 一次生成 value 与 onValueChange。风险：只写 _bindable 不写回调，则调用方绑不上（报错），
   写了回调不用 _bindable 则类型放行（运行时诊断）。_bind 的目标必须是可写变量，类型层同样看不到（_bind(a + b) 放行）。
   Bound<T> 对 T 不变（函数类型属性逆变）：`string` 变量绑不到 `'sm'|'md'` 的 prop；可绑定的数组 prop 要声明成可变数组（string[]），readonly string[] 的 prop 绑不上 string[] 变量。
4. 事件后缀：每个事件展开 4 个键（×16 含组合）每个标签有 440~1760 个键，成本太高（第四节）。最终方案：
   - 无后缀：全部事件精确类型（110 个键）。
   - 单个后缀：常用 33 个事件（click、keydown、focus、pointerdown、wheel、touchstart、scroll…）精确类型（99 个键），其余事件走 3 个模式索引签名。
   - 组合后缀（顺序随意）：12 个模式索引签名。
   模式索引签名的限制：后缀前的事件名不检查（onClikCapture 过得去，重复后缀 onClickCaptureCapture 也过得去）、事件对象是通用 Event
   （要精确类型就标注参数，且要带 currentTarget：(e: MouseEvent & { currentTarget: HTMLDivElement }) => …；方法签名的双向协变保证这样的标注能通过）。
5. 没有 token 的属性写错关键字不报错（display: 'flxe'）：csstype 的取值是开放字符串（string & {}）。有 token 的属性靠“不以下划线开头的字符串”模板联合
   （NotToken）才能拦住 '_mdd'，副作用是这类属性的关键字补全消失（但仍合法）。
6. 以插值开头的模板字符串写在有 token 的属性上被拒（`${t.space.md} 0` 的类型是 `${string} 0`，可能以 _ 开头）；包进 calc() 或放在字面量后面即可。
7. 带组名的写法 '_space.md' 只校验组名，不校验组里的 token 名。全部列成字面量联合会让每个有 token 的属性补全多出 60 多条带组名的条目，排在 '_md' 前面
   （v0 里实测，padding 补全 72 项）；改成模式 `_${组名}.${string}` 后补全只剩 8 项。写错的 token 名由引擎在第一次用到时报错（tokens.ts 的 resolveToken）。
8. 静态样式（create 的静态条目、sx 对象字面量）不收 string 变量，动态样式（函数）才收；静态样式里不能写 --x（有索引签名会让弱类型检查失效）。
9. data-* 用模式索引签名登记取值（false 合法）；其它连字符属性 JSX 本身不检查。
10. 同名标签 a、script、style、title 在 HTML 与 SVG 里重名，按 HTML 处理。
11. 组件 props 的联合属性表（<input> 的 type 分支，8 个变体）：不能给 JSX 的 LibraryManagedAttributes 无条件套映射，
    否则 `<input />` 报 TS2590（联合过于复杂，TS 6 / 7.0 / 7.1 都是）。原生元素传进来的 C 是属性类型本身（不是函数），只对函数组件做 _bind 映射。


三、方案选择与理由
------------------

1. defineTokens 的返回如何驱动 token 类型：选“声明合并 + typeof 登记”，不选泛型。
   做法：`export const t = defineTokens('vtp', {...}); declare module '@hilt/css' { interface TokenSets { vtp: typeof t } }`（一行）。
   类型层从 TokenSets 里算出每组的名字，再用模板字面量加 `_` 前缀；条件别名同理（ConditionSets）。
   理由：
   - API.md 里 create / recipe 是从 '@hilt/css' 全局导入的，token 本来就是全局登记（运行时 registerTokenGroup 也是全局表），类型层与运行时同构；
     泛型方案要把 create/recipe/sx 的类型全部绑到某个 t 上（`const { create, recipe } = createCss(t)`），改变导入方式，每个组件文件都要从应用自己的模块导入。
   - 单一来源：token 名只在 defineTokens 里写一次（对照 06 的做法：手写接口成员，名字写两遍）。
   - 多库共存：登记键是任意名字，组件库与应用各登记各的，类型层把它们合起来；手写联合做不到合并，接口成员可以。
   代价：多一行登记；登记是全局的，同一程序里两套互不相干的 token 会混在一起补全（泛型方案能隔离）。
   token 补全用模板字面量联合 vs 普通联合：成本几乎一样（第四节：N=300 检查 2.05 vs 2.08 s，实例化 648k vs 650k），所以选模板字面量（单一来源）。
2. 元素属性表：自写子集，不用 @types/react 的属性表（那是 React 拼写，我们要的是 class / for / readonly 这类 HTML 原名），csstype 只用在样式取值上。
   csstype 全量 vs 精简（约 190 个常用属性）：N=1000 检查 6.12 vs 5.50 s（-10%），内存几乎一样，实例化 -2%。收益有限，但丢掉关键字补全（display 补全从 41 项
   降到 11 项，精简版的关键字是手挑的几十个），所以默认用 csstype 全量，精简版仅作为可切换的对照（perf/variants.mjs）。
3. 事件后缀：见第二节第 4 条与第四节。
4. 类型文件按职责分目录：types/（核心、符文、JSX）、types/elements/（属性、事件、HTML、SVG）、types/css/（取值、token、条件、create/recipe、theme、登记处）。
   性能相关的开关（属性表、token 类型、NotToken、事件）都放在独立文件里，用 tsconfig 的 paths 可以整体替换（perf/variants.mjs 就是这么做对照的）。
5. 属性值规则与 09-attr 规则表同源：布尔属性用 BoolAttr（boolean | ''），枚举型用 Booleanish；token 的“属性 → 组”对照表由 scripts/gen-property-groups.mjs
   从 10-css/engine/token-map.ts 生成（--check 校验同步），事件驼峰表由 scripts/check-events.mjs 对照 lib.dom 校验，布尔属性与 React 拼写用例由
   scripts/gen-attr-cases.mjs 从属性规则表生成。

4.3 最贵的类型与优化前后

定位方法：perf/ablate.mjs 逐项去掉一类写法（N=100，3 轮中位数，实例化相对 none 的百分比）；--generateTrace + perf/trace.mjs 看节点自身耗时。

优化前（v0）                                      优化后（base）
  none                      100%（2.59 s）          100%（1.12 s）
  去掉 HtmlProps 转发       44%   （-56%）          69%   （-31%）
  去掉受管属性 Omit         74%   （-26%）          99%
  去掉使用方文件            96%（时间 -33%）        80%（时间 -23%）
  去掉 recipe               95%                      85%
  去掉 create               98%                      94%
  去掉 SvgProps 转发        89%                      97%
  去掉 _bind / 列表 / 条件 / 事件 / class / style    均在 95~100%

（“去掉 HtmlProps 转发”的 200 个错误来自使用方文件缺 props，数字只表示这部分类型的体量。）

最贵的类型 = 带事件的元素属性表经过 `{...rest}` / Omit / interface extends 在每个组件里重复做 O(键数) 的工作：
  - v0 每个 HTML 元素有 110 个事件 × 16 种后缀排列 = 1760 个事件键，加上其它共约 1930 个属性键；
  - 每个转发 HtmlProps 的组件：Omit（映射 + Exclude 一千多个键）、rest 类型（再造一千多个属性）、
    `<button {...rest}>` 展开（再造一遍并逐个比较）、SvgProps 展开到 <svg>（同上）；
  - trace（v1 状态、单线程、N=100）里组件文件占检查时间的 69%，其中 `<svg {...iconProps} {...s.icon}>` 一个节点每个组件约 9 ms，
    根元素的 `{...s.root} {...rest}` 约 6.5 ms，create 约 7 ms，recipe 约 5 ms。

优化（按顺序）：
  1. 事件后缀的排列从“全部展开成属性”改成“常用事件精确展开 + 其余走模式索引签名”（第二节第 4 条）。
     v0 1760 键 → v1（110 × 4 = 440 键 + 12 个模式）→ base（110 + 99 = 209 键 + 15 个模式）。
     N=1000：检查 15.52 → 9.22 → 6.12 s；内存 2770 → 1118 → 766 MB；符号 5.07M → 2.37M → 1.71M。
     对照（在 v1 上改后缀数，N=1000）：4 种后缀全展开 9.22 s；16 种排列全展开 10.25 s；只有无后缀（110 键）5.63 s。
     观察（原因没有查清，不当作结论）：v0 的“16 种排列全展开、没有模式签名”是 15.52 s，加上 12 个组合后缀的模式签名后（属性仍是 16 种展开）
     N=100 实例化 990k → 563k，N=300 检查 5.56 → 3.27 s；键数从 440 到 1760 之间的耗时几乎不变（9.22 vs 10.25 s），而从 110 到 440 差很多（5.63 vs 9.22 s）。
     成本不是随键数线性增长，我没有隔离出原因（试过：给目标类型加不匹配任何属性的模式签名没有效果，说明不是“有索引签名”本身）。
  2. 去掉 JSX.LibraryManagedAttributes 对原生元素的映射：TS2590 的正确性修复，同时避免联合属性表上的全量映射。
  3. BoundProps：先用模式交叉在回调键里筛出 xxx，再检查 xxx 是不是 props 的成员（原来 `on${string}Change` 把原生 onChange、onSelectionChange 都当成可绑定回调）。
     N=100 实例化 -0.4%，不是热点；保留是为了语义准确（原生 onChange 不再触发映射）。
  4. 已试过、没采用：
     - 用交叉类型代替 Omit（`P & { [K in Managed]?: never }`）：实例化 -18%，但检查时间 1.61 → 1.85 s（交叉类型的关系检查更慢），补全里还会留着被“删掉”的属性，放弃。
     - 非媒体元素去掉 22 个媒体事件：实例化 -7%，时间在噪声内，没有采用。
     - 去掉 52 个 React 拼写提示键：时间在噪声内。
  5. “属性 → token 组”从一开始就用反向表（PropertyGroupOf，属性查组是一次属性查找）；按组存属性名联合再逐组判断 extends 的朴素写法我没有单独量，不报数字。

五、没有验证 / 需要注意
-----------------------

- 合成组件库的结构高度一致，真实库的类型多样性更高；绝对数字请只当量级。
- 没有量：声明文件生成（--declaration）、增量构建（--incremental / --build）、包含 .d.ts 发布后的消费者场景（组件库以 d.ts 形式被应用引用时的成本）。
- 编辑器里的真实体验（WebStorm / VS Code 对 TS 7.1 LSP 的补全排序、JSDoc、跳转定义）没验证；LSP 延迟是直接发协议请求的结果。
- token 的悬停文档：token 登记只有名字，没有值的说明（原 06 用 JSDoc 写在接口成员上，defineTokens 驱动后值只在 defineTokens 的调用处）；没做。
- 多线程检查器的实例化数含重复计数，不同线程配置之间不能直接比实例化。
- 机器干扰：同时有 IDE 和别的 tsc 进程在跑；表中 3 轮最小~最大给出了抖动范围（多数 ±5%，个别 ±15%）。
- 事件模式索引签名为什么能把 16 种排列全展开的成本拉下来（4.3 节观察），没有查清原因；如果以后升级 TS，这条要重测。
